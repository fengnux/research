## Lab 03b 設計重點

### 為什麼把 APIs 拆成獨立 stack

`google_project_service` 是「啟用 API」的宣告。與消費它的資源（VPC / GKE / Cloud SQL）放同一 stack，會讓「加一個新服務」變成「在不同 stack 各自加一行 API」，散在多處難管。

獨立成 `stacks/dev/apis`：

- 加新 API 只改一個檔
- 其他 stack 用 `after = ["/stacks/dev/apis"]` 表達依賴，順序由 Terramate 保證
- `disable_on_destroy = false` 統一設定（避免 `tofu destroy` 把整個 project 的 API 關掉）

### CIDR 規劃（dev VPC）

| 用途 | CIDR | 大小 | 說明 |
|------|------|------|------|
| Subnet primary（節點 / VM） | `10.10.0.0/20` | 4096 | asia-east1 |
| Secondary `pods`（GKE alias IP） | `10.20.0.0/14` | 262144 | GKE VPC-native 必需 |
| Secondary `services`（GKE ClusterIP） | `10.30.0.0/20` | 4096 | GKE VPC-native 必需 |

GKE secondary ranges 雖然技術上可等 GKE lab 再 in-place 加，但本 lab 一次寫好避免回頭改 network stack。

### 防火牆與 NAT

- **`allow-iap-ssh`**：source `35.235.240.0/20`、target tag `iap-ssh`、tcp:22；只有 attach `iap-ssh` tag 的 VM 才接受
- **Cloud NAT**：`AUTO_ONLY` / `ALL_SUBNETWORKS_ALL_IP_RANGES` / `ERRORS_ONLY` log（避免 dev 噪音 / 費用）

### 驗證 03a 的 generate 邏輯

順便驗證 [Lab 03a](../lab-03a-state-migration.md) 在 root 寫的 `_terramate_backend.tf` 自動生成邏輯，在巢狀路徑下會正確產出兩段不同的 GCS prefix（`dev/apis` 與 `dev/network`）。

## Change Detection 文件重點

### 核心機制

純 git-based，不看 tofu state、不 watch 檔案系統：

1. 預設 diff 範圍 = `HEAD vs merge-base(HEAD, origin/main)`
2. 列出改動檔案路徑（等同 `git diff --name-only`）
3. 每個改動檔，從目錄往上找最近的 `stack.tm.hcl`，那個目錄就是被影響的 stack
4. 加入額外觸發：`stack.watch`、`import` 來源、root `generate_hcl` 規則改動（透過 generated 檔 diff 連帶觸發）
5. 依 `after` / `before` 排 run order（**change detection 不會把上游拉進來，只是排序**）

### Main-only 開發盲點

| 情境 | HEAD | merge-base | diff |
|------|------|-----------|------|
| feature branch | branch tip | 從 main 分岔點 | branch 上所有 commit ✅ |
| 在 main commit、未 push | main tip | origin/main（落後 N commit） | 本地未推的 N 個 commit ✅ |
| **在 main commit、已 push** | **main tip = origin/main** | **自己** | **空 ❌** |

第三種就是「都在 main 開發」的盲點：push 完之後 `--changed` 偵測不到任何 stack——這是刻意設計（合進 main 後就「不是變更」了）。

### 替代基準

| 方式 | 用法 |
|------|------|
| CLI flag | `--git-change-base=HEAD~1`（看最新一個 commit） |
| Deploy tag | `--git-change-base=last-deploy`，每次 deploy 後推進 tag |
| Repo 預設 | `terramate.config.git.default_branch_base_ref` |
| 不用 `--changed` | 全跑——`tofu plan` 本身會 no-op 沒改的 stack |

### 取捨

- **優點**：純 git、可重現、CI 友善
- **缺點**：跨 stack 邏輯依賴不自動展開（network 改 CIDR 不會連帶 plan 下游 VM stack）——靠 `stack.watch` 或全跑
