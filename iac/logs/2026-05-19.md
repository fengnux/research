## 設計討論

### WIF 是否模組化？結論：不抽

- WIF stack 只有 1 個 instance（單一 CI 信任邊界），沒有具體的第二個 instance 需求 → 抽 module 是過早抽象，違反 Lab 05a「v1 跟現狀 1:1」原則
- WIF 是 ADR-003 foundational stack，refactor 風險高（`moved` block 對 `for_each` map key 改寫複雜）、收益不對等
- 真實重複只在「3 個 SA × 各自一組 binding」，可用 stack 內 `for_each over locals` 收拾，不需要外抽 module

### GKE 用官方 module 還自寫？結論：自寫薄殼

- 官方 `terraform-google-modules/kubernetes-engine` 100+ variable，lab 規模 90% 用不到
- 自寫與 Lab 05a network module 同等抽象層（5-7 個 resource），符合「v1 1:1、需求驅動加 flag」哲學
- 未來真的上 production 規模再評估換 official

### 設計決策（透過 AskUserQuestion 收斂）

| 主題 | 選擇 | 理由 |
|------|------|------|
| Cluster 形態 | **Autopilot** | module 變薄（1 cluster + 2 data source），無 node pool；計費單純，lab 完即 destroy 控成本 |
| Region/cost | **參數化**（location / release_channel / deletion_protection / master_authorized_cidrs） | Autopilot 強制 regional，但 module variable 留彈性給未來 v2 換 Standard |
| Endpoint | **Private nodes + Private endpoint + IAP bastion** | 與既有 IAP/NAT 安全敘事一致；reuse dev-vm 當 bastion |
| 跨 stack 依賴 | **GCP data source**（非 remote_state） | 依賴雲端真實狀態、無 state bucket 權限耦合、CI plan SA 只需 `compute.viewer` |

### dev-vm 自訂 SA（取代 default compute SA）

原本 runbook 草稿只想對 default compute SA 加 binding，但用戶提出「IaC 研究結束後會頻繁做 K8s 實驗」→ 建專屬 SA `dev-vm@...` 更合適：

- 不污染 default compute SA 權限範圍
- 後續 K8s lab 系列陸續加 binding 不會雪球
- 命名語意清楚（runtime identity）

權限最小集合：`roles/container.developer` + `roles/container.clusterViewer`。

#### 坑二：CI apply 缺 SA 管理權限（403）

dev/vm apply 在第一個 resource 就掛：

```
Error 403: Permission 'iam.serviceAccounts.create' denied 
on resource '//cloudresourcemanager.googleapis.com/projects/research-lab-495809'
```

WIF stack ci 原本只有 `roles/iam.serviceAccountTokenCreator`（只能 mint token），缺：
- `iam.serviceAccounts.create` → 需 `roles/iam.serviceAccountAdmin`
- `resourcemanager.projects.setIamPolicy` → 需 `roles/resourcemanager.projectIamAdmin`
- `iam.serviceAccounts.actAs` → 需 `roles/iam.serviceAccountUser`（掛 SA 到 VM 用）

⚠️ 整個 lab runbook 設計時沒列這三個 → runbook 風險表沒 cover。需回頭補。

## 學到的事

### 1. PR-first 流程下 WIF 權限「chicken-and-egg」

CI apply SA 改自己之外的 SA 時，前置權限若 runbook 沒涵蓋 → CI apply 失敗 → 還是要回 WIF stack manual apply 補 → 多繞一圈。

教訓：寫 runbook 設計階段，每個會被 CI apply 的 resource 都要對應檢視 ci SA 是否有對應 IAM 動作權限。光列「資源變更」不夠，要列「操作該變更需要的 GCP IAM permission」。

### 2. `gh run rerun --failed` 對主幹快速移動的 repo 不可靠

跟 Lab 05a 踩坑三同模式：rerun 重跑的是當時 commit，但 main 已往前 → workflow 內 base-branch check / Terramate change-detection 對不上。對需要重做 apply 的場景，下次優先用「pushing fresh trigger（empty commit / stack trigger）」而非 rerun。

### 3. State 空 ≠ State 損毀

`tofu state list` 回空時，先確認雲端是否真的不存在再決定 import / 重建。本 project 慣例是運算類資源實驗完即拆（[已記 memory](../../memory/project_teardown_after_lab.md)），看到空 state + GCS file 存在屬正常。

### 4. Autopilot 計費模型對 lab 環境特別需要紀律

Regional control plane ~$73/月（已無 free tier）+ pod-request 計費。一旦忘記 destroy，月帳單立刻有感。runbook Phase G 排 destroy 不是禮貌性步驟，是預算控管硬要求。
